Diapositiva 2: Visión del Negocio y Desafíos de Dominio

HU-01 a HU-11

⚠️ El Problema de Negocio

  • Picos de demanda masiva: cientos de compradores intentando adquirir las últimas entradas al mismo tiempo.
  • Riesgo crítico de overbooking: condiciones de carrera (*race conditions*) que emiten más tickets que la capacidad del recinto.
  • Inconsistencia de inventario: cupos bloqueados indefinidamente si el comprador abandona o falla el pago.
  • Integración bancaria legada: pasarelas SOAP lentas o inestables que pueden colgar hilos del servidor.

✅ La Solución EventHub

  • Reserva Temporal (HOLD stateful): bloqueo atómico de cupo por 5 minutos por tipo de entrada antes de cobrar.
  • Máquina de Estados Finita (State Pattern): transiciones estrictas (PENDING → PROCESSING → PAID / CANCELLED / REFUNDED), devolviendo HTTP 409 ante saltos inválidos.
  • Emisión y Check-in Atómico: códigos QR únicos (EVT-...) con UPDATE ... WHERE status='ISSUED' para impedir doble ingreso.
  • AI Advisor Gateway: recomendaciones personalizadas con enmascaramiento PII y guardrails anti-inyección.

Diapositiva 5: Integraciones (SOAP Legado, REST y AMQP)

SOAP · REST · AMQP

🏦 SOAP Sistema Legado

  • Contrato formal en docs/contracts/payments.wsdl y servicio soap-mock en Compose.
  • Faults Tipados: separa BUSINESS_FAULT (402) de TECHNICAL_FAULT (503).
  • Defensa XXE: rechaza <!DOCTYPE y <!ENTITY con XXE_INJECTION_REJECTED tanto en cliente como en servidor.
  • Higienización: sanitizeSoapMessage limpia XML antes de exponer mensajes.

🌐 REST Moderno + Geocode

  • Contrato OpenAPI 3.1 publicado en GET /openapi.json.
  • Validación estricta con whitelist: true y forbidNonWhitelisted: true.
  • Geocodificación REST: servicio geocode-mock con timeout de 3s y fallback seguro (lat: null, lon: null).

📨 RabbitMQ Topic Exchange

  • Exchange durable eventhub.events de tipo topic.
  • Enruta eventos (order.created, order.paid, order.refunded, event.created) a 2 colas independientes:
  • notifications_queue (emails) y audit_queue (auditoría).

Diapositiva 6: Timeout de 5s, Circuit Breaker y Fallback

503 / 504 + Retry-After
1

Bloqueo Previo

OrdersService.pay toma FOR UPDATE y pasa la orden a PROCESSING antes de cobrar.

2

Validación Luhn + XXE

Rechaza tarjetas inválidas o inyecciones XML antes de abrir conexión externa.

3

Carrera 5.000 ms

Promise.race con timer .unref(). Si SOAP supera 5s aborta sin colgar hilos.

4

Fallback Seguro

Timeout → 504; Circuito abierto → 503. Cabecera Retry-After: 30 y orden vuelve a pending.

⚡ Máquina de Estados del Circuit Breaker

  • CLOSED Operación normal hacia la pasarela SOAP.
  • OPEN Se abre tras 3 fallos técnicos consecutivos (cooldown 30s). Responde fast-fail 503 Service Unavailable.
  • HALF_OPEN Pasados 30s deja pasar una petición de prueba; si triunfa, cierra el circuito.

🛡️ Integridad Durante Contingencia

  • A diferencia de un rechazo de negocio (402 fondos insuficientes, que cancela la orden), ante falla técnica o timeout la orden permanece en pending.
  • El usuario conserva su reserva (HOLD) y puede reintentar el pago cuando la pasarela se recupere.

Diapositiva 7: Transactional Outbox y Caída del Broker

ADR-007 · Cero Pérdida

🔄 Transacción Única ACID + Outbox

  • El Problema: confirmar una orden en PostgreSQL y fallar al publicar en RabbitMQ deja el sistema desincronizado.
  • Solución: dentro de la misma transacción dataSource.transaction donde se guarda la orden (o reembolso), se inserta en outbox_messages con estado PENDING.
  • Dispatcher Polling: OutboxService sondea cada 2s, publica al Exchange Topic y marca SENT tras confirmación.

🧪 Ensayo Real con Broker Apagado

1. docker stop eventhub_broker
2. POST /orders → HTTP 201 Created ✅
   └─ outbox_messages: status = 'PENDING'
3. docker start eventhub_broker
4. OutboxService reconecta automáticamente:
   └─ Publica al topic exchange → status = 'SENT' ✅

Resultado: 0 mensajes perdidos ante caída total o reinicio del broker RabbitMQ.

Diapositiva 8: Consumidores Idempotentes, Topic y DLQ

2 Colas + DLQ Real

♻️ Deduplicación Persistente

  • Columna única messageId en tabla notifications + caché en memoria.
  • Si RabbitMQ reenvía un mensaje o la API se reinicia, detecta el messageId existente, responde DUPLICATE_SKIPPED y hace ack sin duplicar filas.

📡 2 Consumidores en Topic

  • Exchange eventhub.events (topic) distribuye cada evento a:
  • 1. notifications_queue: NotificationsController (emails).
  • 2. audit_queue: AuditConsumerService (registro de auditoría).

☠️ Dead Letter Queue (DLQ)

  • Exchange DLX: eventhub.dlx → Cola durable notifications_dlq.
  • Ante poison pills (payload inválido), reintenta 3 veces y ejecuta nack(requeue: false).
  • RabbitMQ lo mueve a notifications_dlq con cabecera x-death.

Diapositiva 9: Idempotency-Key, ETag y Problem Details

RFC 9457

🔑 Idempotency-Key + Hash SHA-256

Índice único compuesto (userId, idempotencyKey) en orders. Si 5 POST simultáneos llegan con la misma clave, se crea 1 sola orden. Si cambia el cuerpo con la misma clave → HTTP 422.

🏷️ Concurrencia Optimista (ETag / If-Match)

GET /orders/:id expone ETag: W/"1". Al pagar, cancelar o reembolsar con If-Match desactualizado, responde HTTP 412 Precondition Failed evitando *lost updates*.

📋 Problem Details (application/problem+json)

{
  "type": "https://eventhub.com/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "Cannot delete event with existing orders or tickets",
  "instance": "/events/e1",
  "timestamp": "2026-11-27T11:20:00.000Z"
}

Incluso violaciones de BD (23503 / 23505) se mapean a 409 Conflict sin filtrar trazas SQL internas.
