Contexto & Dominio

Visión del Negocio y Desafíos de Dominio

HU-01 a HU-11

⚠️ El Problema de Negocio

  • Picos de demanda masiva: miles de usuarios compitiendo por las últimas localidades en simultáneo.
  • Riesgo crítico de overbooking: condiciones de carrera que emiten más entradas que la capacidad del recinto.
  • Inconsistencia de inventario: cupos bloqueados si el pago falla o el comprador abandona el flujo.
  • Pasarelas bancarias legadas: servicios SOAP lentos o inestables que pueden agotar los hilos del servidor.

✅ La Solución EventHub

  • Reserva Temporal (HOLD): bloqueo atómico de cupo por 5 minutos por tipo de entrada antes de cobrar.
  • Máquina de Estados Finita: transiciones estrictas (PENDING → PROCESSING → PAID / CANCELLED / REFUNDED), devolviendo HTTP 409 ante saltos inválidos.
  • Check-in Criptográfico Atómico: códigos QR únicos (EVT-...) con UPDATE ... WHERE status='ISSUED' para evitar doble ingreso.
  • AI Advisor Gateway: recomendaciones personalizadas con anonimización PII y guardrails de seguridad.

Integraciones Heterogéneas (SOAP, REST y AMQP)

SOAP · REST · AMQP

🏦 SOAP Sistema Legado

  • Contrato WSDL formal (payments.wsdl) y servicio soap-mock en Compose.
  • Faults Tipados: separa BUSINESS_FAULT (402) de TECHNICAL_FAULT (503).
  • Defensa XXE: rechaza <!DOCTYPE y <!ENTITY con XXE_INJECTION_REJECTED en cliente y servidor.
  • Sanitización: limpia XML crudo antes de responder.

🌐 REST Moderno + Geocode

  • Contrato OpenAPI 3.1 en GET /openapi.json.
  • Validación estricta con whitelist: true y forbidNonWhitelisted: true.
  • Geocodificación REST: servicio geocode-mock con timeout de 3s y fallback seguro (lat: null, lon: null).

📨 RabbitMQ Topic Exchange

  • Exchange durable eventhub.events de tipo topic.
  • Distribuye eventos (order.created, order.paid, order.refunded, event.created) a 2 colas independientes:
  • notifications_queue y audit_queue.
Tácticas de Resiliencia

Timeout de 5s, Circuit Breaker y Fallback

503 / 504 + Retry-After
1

Bloqueo Previo

OrdersService.pay toma FOR UPDATE y pasa la orden a PROCESSING antes de cobrar.

2

Luhn + Defensa XXE

Valida algoritmo de Luhn en todos los caminos y rechaza inyecciones XML.

3

Carrera 5.000 ms

Promise.race con timer .unref(). Si SOAP supera 5s aborta sin colgar hilos.

4

Fallback Seguro

Timeout → 504; Circuito abierto → 503. Cabecera Retry-After: 30 y orden en pending.

⚡ Estados del Circuit Breaker

  • CLOSED Operación normal hacia la pasarela SOAP.
  • OPEN Se abre tras 3 fallos técnicos consecutivos (cooldown 30s). Responde fast-fail 503.
  • HALF_OPEN Pasados 30s prueba una petición; si triunfa, cierra el circuito.

🛡️ Preservación de Reserva

A diferencia de un rechazo de negocio (402, que cancela la orden), ante falla técnica o timeout la orden permanece en pending conservando el HOLD para que el usuario reintente.

Tácticas de Resiliencia

Transactional Outbox y Caída del Broker

ADR-007 · Cero Pérdida

🔄 Transacción Única ACID + Outbox

  • El Problema: confirmar la orden en PostgreSQL y fallar al publicar en RabbitMQ desincroniza el sistema.
  • Solución: dentro de la misma transacción dataSource.transaction donde se guarda la orden (o reembolso), se inserta en outbox_messages con estado PENDING.
  • Dispatcher Polling: OutboxService sondea cada 2s, publica al Exchange Topic y marca SENT tras confirmación.

🧪 Ensayo Real con Broker Apagado

1. docker stop eventhub_broker
2. POST /orders → HTTP 201 Created ✅
   └─ outbox_messages: status = 'PENDING'
3. docker start eventhub_broker
4. OutboxService reconecta automáticamente:
   └─ Publica al topic exchange → status = 'SENT' ✅

Resultado: 0 mensajes perdidos ante caída total o reinicio del broker RabbitMQ.

Mensajería Confiable

Consumidores Idempotentes, Topic y DLQ

2 Colas + DLQ Real

♻️ Deduplicación Persistente

  • Columna única messageId en tabla notifications + caché en memoria.
  • Ante redelivery o reinicio de la API, detecta el messageId existente, responde DUPLICATE_SKIPPED y hace ack sin duplicar filas.

📡 2 Consumidores en Topic

  • Exchange eventhub.events (topic) entrega cada evento a:
  • 1. notifications_queue: NotificationsController (emails).
  • 2. audit_queue: AuditConsumerService (auditoría).

☠️ Dead Letter Queue (DLQ)

  • Exchange DLX: eventhub.dlx → Cola durable notifications_dlq.
  • Ante poison pills, reintenta 3 veces y ejecuta nack(requeue: false).
  • RabbitMQ lo transfiere con cabecera x-death.
Contrato HTTP

Idempotency-Key, ETag y Problem Details

RFC 9457

🔑 Idempotency-Key + Hash SHA-256

Índice único compuesto (userId, idempotencyKey) en orders. 5 POST simultáneos con la misma clave crean 1 sola orden. Si cambia el cuerpo → HTTP 422.

🏷️ Concurrencia Optimista (ETag / If-Match)

GET /orders/:id expone ETag: W/"1". Pagar, cancelar o reembolsar con If-Match desactualizado responde HTTP 412 Precondition Failed.

📋 Problem Details (application/problem+json)

{
  "type": "https://eventhub.com/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "Cannot delete event with existing orders or tickets",
  "instance": "/events/e1",
  "timestamp": "2026-11-27T11:20:00.000Z"
}

Violaciones de BD (23503 / 23505) se mapean a 409 Conflict sin filtrar trazas SQL.
